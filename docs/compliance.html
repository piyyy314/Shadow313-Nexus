Security & Standards Notes

Implementation notes for selected cryptographic and security controls in the Shadow313 NEXUS source repository.

Important scope limitation

This page is not a compliance assessment, certification, attestation, authorization, or statement of conformity. Shadow313 NEXUS is not represented as FIPS-validated, FedRAMP-authorized, CMMC-certified, SOC 2-audited, or PIPEDA-certified. Previously displayed coverage figures and green control statuses were not independently assessed and are withdrawn.

Cryptographic implementation boundaries

NIST FIPS 203 (ML-KEM): defines a key-encapsulation mechanism. The presence of a dependency or documentation does not establish that the application uses a validated module or negotiates ML-KEM in production.

NIST FIPS 204 (ML-DSA): defines a digital-signature algorithm. The API demo receipt is not ML-DSA-signed. Do not label HMAC or a placeholder adapter as ML-DSA.

NIST FIPS 205 (SLH-DSA): defines a stateless hash-based signature algorithm. The API receipt route explicitly labels its output UNSIGNED-SHA3-512-DEMO; it does not create an SLH-DSA signature.

Algorithm support must be established from the exact code path, installed implementation, test vectors, key lifecycle, and independent validation—not from a badge or package dependency.

What is required for a real assessment

  • Define the system boundary, deployment architecture, assets, data flows, and control owner.
  • Map implemented controls to the applicable baseline using evidence.
  • Test identity, authorization, secrets, logging, retention, backup, incident response, and operational procedures.
  • Have the appropriate independent assessor or authorizing body perform the required review.
  • Publish scope, evidence date, exceptions, and assessment status without implying certification.

Evidence sources

Use the API contract, API implementation, README, and exact-commit CI results. Passing CI is software test evidence, not a compliance certification.
